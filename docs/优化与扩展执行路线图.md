## 1. 我的判断

当前项目值得继续沿用 Go 单体、PostgreSQL 任务队列和 Vue 原生组件。批次练习、答案分层、不可变版本、AI 私有出题、题目解析缓存、学习记忆和管理员用量统计都已经存在，继续增加框架或重写架构的收益很低。

最有价值的下一步，是让用户稳定完成这个循环：**答案不丢 → 结果可信 → 知道为什么错 → 直接开始合适的下一批 → 过几天验证是否记住。** 现阶段既有统计和保存方面的具体缺口，也有“看完结果后没有明确下一步”的产品缺口。修正这些，比增加一个聊天入口更能改善刷题体验。

如果预算只够一轮，先完成 **D00、T01–T07**；接着做 **T08–T11 和 F01**。AI 质量与成本任务可以按实际使用量插入。F02–F05 属于后续候选，不要求一次全部实现。

本文所说的“执行模型”是替你修改代码的模型；A01–A03 中评估的是产品运行时调用的 AI。两者应分开决策，不需要一起更换。

## 4. 所有执行任务共用的边界

1. 优先遵守当前 `AGENTS.md` 和用户最新要求。旧规范与代码不一致时，先记录差异；不能仅为了符合旧文档而恢复已移除能力。本文的新增产品规则是建议，只有用户选择相应任务时才实施。
2. UI 使用“刷题 / 答题 / 提交本批练习”等既定术语。答题前不出现答案、解析、判分、非原题翻译或可推断答案的提示。
3. 用户答案、权威答案、AI 候选答案是不同的数据结构和可信层级。`confirmed` 只含权威确定性结果，AI 结论显示“AI 判定(可能有误)”。
4. 题目修改创建新版本；旧批次保留原版本。迁移只能追加，编号以执行时目录为准，不能修改 `0001`–`0003` 等已经存在的迁移。
5. 统计从作答事实重建，不能在保存/提交接口直接累加正确率。软删除不删除成绩事实；学习记忆重置要遵守 `reset_at`。
6. 每次新提交保留一个 `analyze_practice_session_ai` 批次任务；原有统计任务另算。重试可以产生可追溯的新尝试，但同一批不能有多个活动分析任务。不得重新引入逐题 AI 入队。
7. 学习者资源在 SQL 中按用户隔离；写请求经过 Origin、Cookie 和角色校验。未知字段、错误类型、非法范围仍须在后端拒绝。
8. 复用 `request<T>`、`formatAIText`、现有 CSS token 和原生表单控件；触控目标至少 44px。不要新增 UI 库、状态库、ORM、队列服务或通用工作流框架。
9. 本轮不改生产配置、不重新导入题库、不清理运行数据、不发布。集成测试仅使用独立可销毁测试库，绝不能把开发库或生产库地址传给会清库的测试。
10. 每次只执行一张任务卡；L 任务只执行一个子步骤。任务附带的回归检查必须能区分修复前后，不能用修改期望值掩盖错误。

### T02 — 自动保存覆盖离开页面和提交边界

**依据：** `useAnswerAutosave.schedule` 先等 500ms，只有请求失败才写草稿；`PracticePage` 卸载时直接取消 timer。因此修改后迅速离开页面，会丢失尚未发出的修改。`openConfirm` 又 `await flushPending`，慢保存会延迟提交确认，虽然提交接口本来就接收全部答案。

**T02a，修改保全：** 在修改进入未同步状态时保存最小本地草稿；请求成功只清理该请求确认的版本，不能清除期间又产生的新修改。明确处理同组件切换批次、路由离开、刷新和提交成功后的旧响应。已提交批次不恢复草稿，晚到的保存失败不能重新生成已清理草稿。

**T02b，提交：** 取消 debounce 后直接打开确认，提交发送当前完整答案，不等所有 PUT 完成。保留并发提交保护。`localStorage` 读写不可用时，以组件内的固定幂等键完成本次提交并允许重试；不要让存储异常阻止发送请求，也不要声称这种情况下支持跨刷新恢复。

**验收：** 用假 timer 和可控 Promise 覆盖：修改后 100ms 离开并恢复；A 保存中改成 B，A 成功不能清掉 B；PUT 长时间不返回仍能提交；成功后晚到的 PUT 不恢复草稿；同组件从批次 A 到 B 不串答案；存储抛异常时仍可提交。保留“最终提交答案胜过自动保存”的后端检查。

**范围：** [useAnswerAutosave.ts](../front-web/src/features/practice/useAnswerAutosave.ts)、[PracticePage.vue](../front-web/src/features/practice/PracticePage.vue)、`front-web/tests/autosave.spec.ts` 及最小页面测试。只做未同步答案的恢复，不增加离线题库。

### T03 — worker 在空队列、崩溃和租约过期时能够恢复

**依据：** [worker.go](../backend/internal/jobs/worker.go) 仅在成功领取新任务后调用 `ReleaseExpired`。当库里只剩过期的 `running` 任务时，没有新任务就不会回收。当前又在占用并发槽前领取任务，使任务等待执行时已经消耗租约；[queue.go](../backend/internal/jobs/queue.go) 的 Complete/Fail 仅按 ID 更新，缺少领取者和尝试号限制。

**T03a，领取和回收：** 用固定 worker 槽位或先获得槽位再 Claim，避免提前领取；无论是否领到新任务，都低频执行过期回收。等待槽位必须响应取消。回收尊重最大尝试次数，不能通过反复崩溃无限重试。

**T03b，完成与业务写回：** 利用现有 `locked_by + attempts` 标识一次领取，在 Complete/Fail 时校验当前所有权；处理器运行时间与租约留出收尾余量。旧领取的业务写回也要在同一落库事务内验证所有权，不能只保护 jobs 状态。最终失败要让对应练习进入可理解的失败状态，不能只把 jobs 标红而让练习永久处理中。取消后的收尾使用有短超时的独立上下文。

**验收：** 专用库中只有一条过期 running 任务也能自动恢复；并发为 1 时不会把第二条任务提前设为 running；A 过期、B 重新领取后，A 不能覆盖 B 的任务或业务结果；最大重试后收敛到终态；关闭 worker 不阻塞。测试用短租约，不真实等待 10 分钟。

**复核重点：** 这是本轮最需要认真复核的并发任务。保留 PostgreSQL 队列，不引入外部消息队列，也不为了处理长任务默认无限续租。

### T04 — 修正连续错误的 SQL

**依据：** `learning.Store.RebuildUserStatsTx` 中按时间倒序编号，却用 `COUNT(*) - MAX(正确位置)` 计算连续错误。按“最新 → 最旧”的序列 `[错, 错, 对, 错]`，当前表达式得到 1，正确结果应为 2；`[对, 错, 错]` 当前得到 2，应为 0。

**最小实现：** 倒序中找到最近一次正确的位置，取它之前的错误数；全错时取总数。排序加入固定的批次/题目顺序和唯一 ID，避免同批 `submitted_at` 相同导致结果漂移。同批按题号定义统计顺序，说明这是确定的统计约定，不是采集到的真实答题时间。

**验收：** 上述两例、全错、全对、权威未答、混有 AI 结果、相同提交时间均有 SQL 集成用例。AI 结果不改变已确认连续错误。修复已有用户缓存只能触发统计重建，不能改原始成绩。

**范围：** [learning/store.go](../backend/internal/learning/store.go) 的重建 SQL 和最小集成测试；不增加新表。

### T05 — 账号总题数不能把知识点计数相加

**依据：** `MemoryForUser`、`MemorySnapshotForAI`、`GenerationMemoryForAI` 均通过 `sum(user_knowledge_stats.confirmed_answered)` 读取账号总数。一道题关联两个知识点时会计两次；没有知识点的题则不计入。首页显示的是“题”，目前与事实口径不一致。

**最小实现：** 账号总数从用户的练习题目和有效判分事实聚合，以一次作答的 `practice_item` 为单位；同一道题跨批次作答分别计数。同一次作答若有多个来源记录，明确按权威优先规则选择，避免混合估算重复计数。知识点内统计仍保留多对多关联的原口径。

统一三个调用方使用的账号聚合方法，包含 `reset_at`、批次提交状态和来源分层；不能用 `sum(distinct count)` 修补。软删除练习不删除这些事实，未提交练习不计入。

**验收：** 一题关联两个知识点：账号总数 +1，两个知识点各 +1；无知识点题仍计入账号总数；另加一题 AI 判定只增加 AI 数量；重置前数据不进入新记忆。首页、AI 总结输入和出题记忆输入使用相同口径。

**范围：** `learning/store.go`、相关 DTO（仅确有字段变化时）和数据库测试。读取事实聚合不等于在答题路径上修改统计缓存。

### T06 — AI 完成后及时重建学习统计

**依据：** `handleBatchAnalysis` 在调用模型前重建统计，成功写回 AI grades 后没有再入队重建任务。提交时原有的重建任务可能已经执行，因此新 AI 判定不会保证立即进入知识点统计，可能要等下一次练习触发重建。

**最小实现：** 在 AI 判分成功写回的同一事务中，入队 `rebuild_user_knowledge_stats`；失败重试后成功也走此路径。考虑处理器重复运行时不要产生无意义的重复重建，且原来的记忆重置边界不能被旧任务越过。

**验收：** 用固定 AI 响应处理一个包含无权威答案题的批次，排空其队列后，在不创建新批次的情况下查询知识点和账号记忆，AI 数量已经正确；正式正确率不变；重试成功同样成立。验证 AI 批次任务仍只有一个，统计任务数量单独核对。

**范围：** [ai/service.go](../backend/internal/ai/service.go)、`learning` 现有重建入口和集成测试。不顺便删除提交阶段的重建或重做任务编排。

### T07 — 填空答案和简答参考内容能在结果中看到

**依据：** 后端 `Grade` 会保留标准答案原结构，填空是 `{"acceptable":["..."]}`，简答参考可为 `{"reference":"..."}`。前端 `AnswerValue` 与结果/错题页的展示逻辑只处理 `optionIds` 和 `text`，合法参考答案可能显示成“—”。

**最小实现：** 为答题后的答案单独定义类型，覆盖 `optionIds`、`text`、`acceptable`、`reference`；保持用户作答和答题前 DTO 的类型严格。结果页与错题页复用一个最小格式化函数，填空列出可接受答案，简答标为参考答案。AI 给出的答案使用 AI 参考标签，不能因字段名 `correctAnswer` 而统一展示为权威标准答案。

**验收：** 结果页和错题页都正确显示选择题、多个可接受填空值、简答参考、AI 文字答案、pending 和失败回退；新类型没有流入答题前 DTO。补充真实答案结构的组件测试，运行前后端 DTO 泄漏检查。

**范围：** [types.ts](../front-web/src/api/types.ts)、[format.ts](../front-web/src/app/format.ts)、[ResultItem.vue](../front-web/src/features/practice/ResultItem.vue)、[WrongItemsPage.vue](../front-web/src/features/practice/WrongItemsPage.vue)、相关 OpenAPI schema。

### T08 — 错题列表和重练使用同一套规则

**依据：** `learning.Store.WrongItems` 和 `practice.Store.WrongQuestionIDs` 都先筛错误再取最新，会继续拿到后来已经答对的旧错误；后者还先对全账号错题 LIMIT，再由选题逻辑筛级别/科目，可能漏掉所选范围内足够多的错题。`WrongItemsPage.retrain` 未传递页面已有的知识点、日期和关键词筛选，且直接使用账号默认级别。两条查询对记忆重置的处理也不一致。

**T08a，状态口径：** 以重置边界后的最新有效作答确定“当前待重练”；pending/failed 不算已经掌握。先确定最新有效结果，再判断是否错误；排序依据作答提交时间及稳定次序，不能让旧题解析稍后更新的 `gr.updated_at` 改写作答先后。保留查看历史错误的能力，并明确定义 `includeCorrect` 为曾错过且现已答对的记录，避免混入从未答错的题。

**T08b，范围一致：** 先应用用户、级别、科目、知识点、日期、关键词和可练版本条件，再计算 availability 和 LIMIT。让错题页的重练操作沿用当前筛选；跨级别列表需要先选级别，不能悄悄回到默认级别。重用一个由业务模块拥有的候选查询，避免复制两套判定 SQL。

**验收：** 错→对退出待重练，对→错重新进入；pending 不抹掉之前的错误；重置前、已隐藏和已下架题不会被重新选中；目标级别的错题排在全局前 10 条之后仍能被选到；预览题量与实际候选一致；筛选后重练不换范围；多知识点题不随机丢失其展示标签。新练习仍使用允许选用的当前已发布版本，历史记录保持旧版本。

**范围：** `learning/store.go`、`practice/service.go`、`practice/store.go`、`content` 选题入口、错题页和契约。先把 T08a 的行为固定并测试，再做 T08b。

### T09 — 旧请求不能覆盖新选择，轮询失败不能抹掉成绩

**依据：** `CreatePracticePage` 做了 debounce，但 availability、来源、知识点请求没有防止旧响应覆盖新筛选；`PracticeResultPage` 使用固定 interval，没有在途保护和请求取消，静默轮询失败会切换整页错误。`PracticePage` 的生成轮询已有 `loadSequence`，可参考其做法。

**最小实现：** 用 `AbortController` 或请求序号丢弃旧读取结果；筛选改变时立即将旧 availability 置为不可用于创建。结果轮询一次只发一个请求，页面隐藏暂停，恢复后刷新；卸载或切换路由参数时取消并使旧响应失效。已有结果在短暂网络错误时保留，并显示轻量重试状态。创建页加载失败的按钮应真正重新请求 catalog。

**验收：** N5 慢响应晚于 N4 快响应时仍显示 N4 数据；进行中的 availability 不能让旧数量解锁按钮；轮询不会重叠；失败时确定性结果保留；completed 后停止；同组件换 sessionId 读取新批次且不被旧响应覆盖。

**范围：** 创建页、结果页、确有同类问题的答题页路由读取。先局部实现，不新增全站请求缓存或轮询管理器。

### T10 — 只有几道题也能开始练习

**依据：** 普通 `practice.validCounts` 只允许 10/20/30，知识点详情固定创建 10 题。一个知识点若只有 3 或 7 道已发布题，当前无法组成专项批次，也无法实现“确认实际可用题量后开始”。

**建议的新产品规则：** 普通题库允许整数 1–30，界面快捷选项为 5/10/20/30，默认仍为 20。题量不足时显示实际数量，用户明确点击“练习现有 N 题”；0 题不能开始。后端仍拒绝超过可用量的请求，不能悄悄缩题或扩大范围。AI 出题暂保持原有 10/20/30 限制，前端单独保留合法 AI 题量。

**最小实现：** 修改普通批次请求校验、OpenAPI、创建页和专项入口；availability 与 count 解耦，只计算该范围实际候选。没有必要增加新的短批次实体。

**验收：** 1、3、7、10、20、30 道普通练习可创建和提交；0、31、负数、小数拒绝；只有 7 题请求 10 题得到明确不足提示；用户确认后才创建 7 题；AI 入口不收到 5 或 7 这样的非法 count。

### T11 — 推荐内容能直接变成下一批练习

**依据：** 首页推荐只有知识点 ID，点击时另取账号默认级别；推荐可能来自其他级别。创建失败后跳到不带范围的创建页，丢失原因与选择。结果页知识点是纯文本，AI 下一步建议也是文本，用户需要自己重新选择范围。

**T11a，范围：** 后端推荐返回实际 `levelId`、`subjectId`、知识点 ID 和可用题量；默认级别只用于新用户起始选择。创建页支持并校验这些 URL 参数。失败跳转时保留范围和推荐原因，只针对明确不足错误提示调整，不能吞掉全部错误。

**T11b，结果：** 逐题知识点链接到知识点详情；结果底部提供“巩固本批相关知识点”和“查看本批错题”等有限行动。由后端根据本批真实结果和题库可用性给出最多 3 项，AI 文本不负责生成可执行 ID。确定性错题优先，AI 判定的薄弱建议单独标明；没有足够数据时提供同范围综合练习。

**验收：** 默认 N5 用户点击 N4 推荐，最终请求仍为 N4；3 道可用题能走 T10 的确认；从结果到专项无需重新选择级别；AI 不可用时行动入口仍可用；未发布知识点、无题和跨账号批次有明确处理。

**范围：** `learning` 推荐 DTO、必要的结果后 DTO、首页、创建页、结果页和知识点链接。结果后新增的范围与建议字段不得添加到答题前题目中。

## 6. AI 质量与成本任务卡

### A01 — 验证答案含义，并区分调用成功与业务成功

**依据：** `handleBatchAnalysis` 已检查 itemId、结论枚举、完整性和文本长度，但 `grades.correctAnswer` 仍是直接写回的 `json.RawMessage`，没有按题型检查选项归属或答案结构。`Client.runPrompt` 在得到合法 JSON 后就记录成功，后续语义校验失败没有关联回该次 `ai_runs`，因此管理页“成功调用”不能直接代表成功生成或分析。

**A01a，语义校验：** 选择题答案只能引用该版本真实选项，单选恰好一个，多选非空且不重复；本批 AI 文字答案按现有协议使用非空、限长的 `text`；`cannot_determine` 允许无答案并保持失败/待人工处理语义。不要把填空标准答案的 `acceptable` 或简答标准答案的 `reference` 校验器直接套在 AI 的 `text` 协议上。可复用 `content.ValidateAnswerValue` 中适用的选择题规则，以及现有严格解码函数。

同时核对权威题解析缓存的约束：缓存文字只解释题目本身，不引用某个学习者的选项或表现。提示词明确区分题目/用户输入与指令，缓存样例加入跨用户检查；权威答案与 AI 有冲突时保留权威结果并进入已有问题反馈流程。

**A01b，审计：** 为一次调用保留可关联的 run ID，记录 HTTP/JSON 处理结果与业务校验结果，区分网络、限流、截断、结构、语义等实际错误。现有 token 和费用记录保留，未配置价格仍显示未知，不能当作免费。取消时如需写审计，使用短超时上下文；不要保存密钥或新增完整用户输入日志。

**验收：** 虚构选项、单选多个答案、空文字、漏题、重复 ID 均不能写残缺结果；错误尝试能与一次实际调用关联；合法 `cannot_determine` 不被误判为接口故障；权威题的最终判分永不被 AI 改写；同版本缓存不带另一位用户的作答细节。

**范围：** `ai/service.go`、`ai/client.go`、适用的共享答案校验、`admin` 审计展示、必要的新迁移。不要在这张卡里更换模型或重写生成提示词。

### A02 — 限制重复生成和单批重试成本

**依据：** `CreateGeneratedSession` 每次请求都会创建新批次，没有账号级生成准入限制。`maxGenerationCalls=6` 与 jobs 默认 `max_attempts=3` 叠加，在持续校验失败等场景下，一次生成理论上可触发 18 次模型请求，人工重新创建还会继续增加。现有管理页已经有用量和估算费用，不必重建一套账单系统。

**A02a，准入：** 服务端以用户行锁或等价的原子条件，保证每账号同时最多一个生成中的批次；重复相同范围请求返回已有批次，不同范围返回明确冲突。增加可配置的每日生成批次数上限，按服务端 UTC 日统计并在界面说明重置时间。可先以每天 10 批作为小范围试用起点，这只是建议默认值，不是已测得的合理配额。失败但实际发起过的生成仍计入消耗，删除记录不能重置额度。

**A02b，调用预算：** 为单个生成批次设置持久化的模型调用总预算，外层 job 重试不能把预算归零；可先设总共 6 次，沿用当前内部上限的量级。每次外呼前原子占用次数，传输状态不确定时按已尝试处理，避免断线绕过限制。给重试中的批次展示已尝试次数和可恢复错误。确定不可恢复的配置/鉴权错误直接收敛，瞬时网络或限流错误有限退避。

未配置 AI 时仍保留正常提交和确定性结果；已经入队的批次分析应快速进入明确终态，不能对同一个配置错误等待多轮。这个降级不增加逐题任务，也不减少已有答案校验。

**验收：** 并发两次创建只得到一个生成批次；日界线与配额行为明确；连续 job 重试的实际外呼次数不超过持久预算；失败、删除、刷新均不能无限刷新预算；普通题库练习、确定性判分和读取历史不受生成配额影响。

**复核重点：** 准入与计数必须原子，不能“先查次数再无锁创建”。网络调用无法靠本地数据库保证外部计费恰好一次；审计需区分确认响应与状态不确定，不能承诺绝对零重复计费。

### A03 — 用固定小样本决定是否能换更便宜的产品内模型

**目标：** 以后调整 prompt 或模型，有依据判断质量和总成本是否改善。单次 token 价格低但经常重试，实际可能更贵。

**最小实现：** 先整理约 40 个固定案例，覆盖四种题型、不同级别、共享阅读材料、无权威答案、歧义题、模型无法判断、异常 JSON、题目内指令文本和重复题。每例保存来源/审核状态、输入、预期可判定结论与结构约束。人工未确认的样例只能测试格式，不能作为日语正确性标准。

用现有 Go 测试、`httptest` 和 JSON 文件跑离线响应回放，默认不调用真实服务。另提供显式开启的评测命令，支持限定案例数与调用次数，记录模型配置、prompt 版本、首次通过率、语义错误数、重复率、耗时、token 和所有重试成本。实际联网评测必须由用户选择模型与预算；本任务默认做到可运行的离线工具和评测模板。

**验收门槛：** 协议、安全和答案隔离测试全部通过；固定的已审核客观题不能出现未解释的新增错误；含糊题能合理拒判。每个候选报告“完成一批可用练习的总成本”，不能只比较一次调用费用。40 例只是回归哨兵，不据此宣称整体教学正确率。

**范围：** `backend/internal/ai` 现有测试、一个小型 testdata 目录和必要的评测入口。暂不增加自动多模型路由、第二模型逐题复核或评测平台。

## 7. 最值得扩展的产品功能

### F01 — 按章节持续推进，避免反复刷同一段题

**为什么做：** 书籍题库的用户需要知道“练到哪里”和“还剩多少”。当前 `SelectPublishedVersions` 在来源顺序下只排除最近 3 批：例如同范围有 100 题、每批 20 题，第 5 批可能重新选到第 1 批，剩余题目得不到优先选择。

**最小实现：** 保持默认 `source_order` 和已有 `random` 行为，新增明确的“未做优先 / 继续本章”选择模式；优先从当前范围内尚未提交作答的题目中按来源顺序选择。用尽后显示完成和复习入口，不在这个模式下默默回到开头。

在来源/章节列表显示当前可用题数、已练不同题数、尚未练题数，复用现有练习事实，不增加学习进度表。以 `question_id` 判定是否练过，跨批重复作答不重复增加覆盖数；按当前已发布版本的章节归属计算分母，下架题不留在待练数量里。软删除不抹去作答事实；学习记忆重置后按新的 `reset_at` 计算本轮进度。

**验收：** 上述 100 题案例中，连续 5 批覆盖 100 个不同 questionId；最后只剩 3 题可经 T10 确认开始；刷新/换设备进度一致；内容下架后分母合理变化；同一题发布新版本不自动重复增加已练数，旧批次内容保持原样。

**范围：** `content` 选题和来源 DTO、创建页、来源章节展示及 SQL 测试。不增加课程实体、路径引擎或强制章节解锁。

### F02 — 用简单规则安排到期复习

**为什么做：** 当前的薄弱点排序和 AI 记忆已经考虑部分近期表现与练习间隔，但没有明确的“这些题今天该复习”队列。题目看懂后隔几天仍能答对，才比立即反复看同题更有学习价值。

**建议规则：** 首版只纳入曾出现权威确定性错误的题目。错误或权威未答后，24 小时后再练；到期后的正确作答依次安排 3、7、14、30 天间隔，连续正确也不早于下一到期时间提前推进阶段；再次错误回到 24 小时。同一天反复答对仍保存作答，但不加速复习阶段。这些是可解释的起始规则，需要观察效果，不能标榜为已验证的遗忘曲线算法。

**F02a，数据和规则：** 增加小表如 `user_question_reviews`，以 `(user_id, question_id)` 唯一，保存阶段、`next_review_at`、最后处理的作答引用和排序依据。复用重建任务按不可变作答序列推导；旧任务或重试不能推进两次。时间存 UTC，间隔明确按小时计算，前端仅本地化展示。记忆重置时对应计划同步重建。

**F02b，页面：** 首页显示到期题量与“复习 5/10 题”，复用现有创建、答题和结果页。候选仍受当前用户、级别、隐藏状态和已发布版本约束；AI-only 错题保留原有独立入口，首版不把 AI 判断当作正式复习阶段依据。

**验收：** 固定时钟覆盖正确推进、错误回退、同日重复、乱序任务、重复重建、重置和下架；一条作答只影响一次计划；0 题显示明确空状态；1–4 题也能开始。上线后观察到期后的再练正确率与完成率，再决定是否更改间隔。

**范围：** 先后端规则/迁移/测试，再前端入口。不做推送、后台通知调度、复杂记忆模型或新的 AI 调用。

### F03 — 导入前提示重复，严格识别完整 JSON

**为什么做：** 同一个文件再次上传与同一个 import item 再次发布是两种问题。当前发布有幂等保护，上传已计算 SHA-256，但 `importJSON` 仍会为再次上传建立新任务。现有解码入口也只 Decode 一次，需检查对象之后的额外内容。

**最小实现：** 使用已保存的文件哈希提示已有任务及状态，允许管理员查看旧任务或明确选择另建；不要把同文件与同题目混为一谈。对单个 JSON 对象后的第二个对象/垃圾内容要求 EOF，复用同模块现有严格解码方法。缺字段、未知字段、超 500 题等原限制保留。

第二步再为审核条目提供“疑似重复”提示：比较题型、题干、选项与材料内容，给出候选题 ID 和来源；相同题干但材料、答案或来源不同只提示。既有 AI 内容复用指纹不直接冒充通用书籍题重复标准，也不自动删题、合并或把公共题转为 AI 私有题。

**验收：** 重复文件能打开已有任务，明确继续时仍保留独立追溯；尾随 JSON 被拒绝；同题干不同阅读材料不会自动合并；AI 建议答案仍须人工审核；共享 `materialKey` 关系保持正确。

**范围：** `imports/json_import.go`、`imports/store.go`、导入页和审核页。继续只接收 JSON，不恢复后端 PDF/DOCX 解析或旧的异步导入重试流程。

### F04 — 把管理员时间用在有疑问的题目上

**为什么做：** 已有逐题保存、审核、发布，不必再搭建后台框架。批量内容多时，减少翻页和重复操作即可明显降低维护成本。

**最小实现：** 导入详情支持按待审核、异常、已审核未发布筛选；审核页提供上一题/下一题，未保存离开时提示。保留保存、审核、发布三个不同动作。增加勾选发布，默认只允许选取已明确审核通过的条目，先顺序调用现有发布接口，每次至多 50 条，显示成功/失败明细。

单条失败不能把整批显示成成功；重试时跳过已发布条目。批量修改先只考虑级别、科目、来源、知识点等有真实重复需求的字段，不让批量操作自动确认所有 AI 答案。并发发布共享材料的正确性未经证明前，顺序执行即可。

**验收：** 用户只选择 5 条就只发布这 5 条；含 1 条失败时明确显示 4 成功、1 失败；重复发布不产生新题；未审核条目无法绕过 service 校验；键盘可以完成切换、保存和审核，手机上能查看原文及字段。

**范围：** `AdminImportDetailPage`、`AdminImportItemPage`，仅当现有服务端分页不支持筛选时补充相应参数。不做表单生成器，也不新增批量自动审核 AI。

### F05 — 看清内容缺口和学习闭环是否改善

**为什么做：** 项目已有用户用量和内容质量概览，但题目总数无法回答“某个级别的哪些知识点真正能练”。同样，AI 调用增加不代表学习效果提高。

**F05a，内容覆盖：** 在现有管理概览增加按级别/科目的表格：已发布公共题数、权威答案覆盖率、至少有 1/5 道可练题的知识点数、没有题的已发布知识点数、待处理举报。复用选题的可用性条件，排除 AI 私有题、下架题和旧版本；每个数字可跳转到相应筛选。

**F05b，产品指标：** 先用现有作答事实计算普通练习开始→提交比例、首次提交用户的 7 日再练比例；用户、批次去重单位明确，AI 生成失败单列，不能混入普通练习完成率。只有从首次提交已满 7 天的用户进入完整 7 日观察分母。

T11 上线后若要衡量“从结果开始下一批”，再在新批次记录经服务端校验的 `originSessionId` 和有限来源枚举；它只用于归因，不继承别人的答案或自动放宽范围。无需添加通用埋点平台。

**验收：** 多知识点题不会放大公共题数；一个用户一天多批不会被计成多个回访用户；不足观察期显示数据不足；关联来源批次必须属于当前用户且已提交；指标明确时间窗口、分母和更新时间。

**范围：** `admin` 现有 store/DTO、内容概览或用户用量页，以及必要的最小来源元数据。使用普通表格，不添加图表库。

## 9. 性能和工程方面，什么时候才继续优化

本次没有测量接口 P95、真实并发或数据库执行计划，不能据文件长度判断性能。当前构建的主 JS chunk 约 107.52 kB、gzip 41.57 kB，页面已有动态路由加载，没有证据支持为首屏重新换框架。

| 观察到的可能增长点 | 先测什么 | 有证据后做什么 |
| --- | --- | --- |
| `loadGeneratedQuestionKeys` 每次读取个人全部 AI 历史并重新解析指纹 | 历史规模、查询耗时、返回数据量 | 优先读取已有 `ai_reuse_key`，只对历史空值补算；保持同账号去重和内容复用的既有语义 |
| 统计重建多次扫描同账号全部记录 | 每批重建次数、耗时、队列等待 | 先合并真实冗余调度或加有依据的索引，保留全量重建作为校验路径 |
| 知识点页面逐行计算题量 | 对代表性数据执行 `EXPLAIN (ANALYZE, BUFFERS)` | 需要时改为一次聚合后 JOIN，数量仍采用可练版本条件 |
| `ORDER BY random()` 随题库扩大变慢 | 真实候选量、筛选后查询耗时 | 证明 SQL 排序成为瓶颈后再替换抽样策略；当前不引入推荐服务 |
| 最近 30 天统计随时间自然过期 | 长期无新作答账号的 `statsUpdatedAt` 与窗口变化 | 显示统计时点；需要严格滚动窗口时，复用重建任务做低频刷新或直接读取窗口事实，不能继续展示过期窗口为实时数据 |
| 长篇阅读和结果页手机体验 | 390px / 768px 的实际阅读与触控 | 修复溢出、材料位置、焦点和按钮尺寸；不先拆出移动端应用 |

性能目标继续沿用原 PRD：普通接口 P95 < 1s、保存 P95 < 500ms、有权威答案的基础结果在提交后 2s 内可见。这些是目标，本文没有给出已经达标的结论。

不安排“把所有大文件拆开”“替换手写 SQL”“引入 Redis/向量库”“统一成低代码后台”等任务。只有具体问题的实现确实需要拆分时，才抽出承担真实职责的函数或文件。

## 10. 按预算执行的建议顺序

### 第一轮：建立可信基线

1. D00：移除会误导执行模型的旧指南。
2. T01：让数据库测试真正运行。
3. T02a/T02b 与 T07：解决用户可直接遇到的保存和答案展示问题。
4. T03a/T03b：解决任务恢复与租约并发。
5. T04、T05、T06：校正统计与更新时机。

完成标准：修改后回归通过，旧答案与历史版本不变，新增一次正常提交仍只有一个批次 AI 任务。先稳定运行，再进入下一轮。

### 第二轮：完成有效的下一批学习

依次执行 T08a/T08b、T09、T10、T11a/T11b、F01。A01 建议在继续依赖 AI 判定前完成；若多人使用或出现重复生成/高费用，A02 提前到本轮。

完成标准：只有几道题也能练，错题和推荐不会换范围，结果页能继续相关练习，同一本书可以持续推进。

### 第三轮：根据使用情况扩展

需要比较产品内模型时做 A03；用户稳定回访后做 F02；管理员导入成为瓶颈时做 F03/F04；要判断迭代效果时做 F05。不要仅为了把路线图清空而一次全部实现。

## 11. 交给便宜模型的复制模板

把 `T04` 替换为本次任务 ID；对于大任务使用 `T03a`、`T08b` 等子步骤。第一次执行先做 D00/T01，之后每次提供对应任务卡即可，不必让模型重新进行全仓库产品分析。

```text
文档基线是 2058abc。若现有代码已经解决问题，先核对任务验收场景，再说明结果，不重复实现。

执行要求：
1. 用不超过 5 行说明当前问题、准备修改的位置和回归方法，然后直接实施。
2. 使用现有模块、原生能力和已安装依赖，保留答案隔离、版本不可变、来源分层和批次 AI。
3. 先增加能覆盖失败场景的最小回归，再修复；不要只调整测试期望。
4. 修改接口时同步 Go DTO、OpenAPI、前端类型及调用方；迁移只能新增。
5. 只在专用测试库运行会清理数据的集成测试。不打印 .env、密钥、Cookie 或真实用户答案。
6. 不重建题库，不清理开发/生产数据，不部署，不顺便升级依赖。

完成后只报告：改了什么；实际测试命令与结果；剩余限制；文件清单。
更新一条该任务的执行记录，不把未执行的验收写成通过。
```

### 每张卡的交付检查

- 前端代码变化：`npm run test` 与 `npm run build`；后端代码变化：`make test` 与 `go build ./...`。最终合并前完成仓库要求的前后端全套检查；纯文档改动核对路径和内容即可。
- 数据库、权限、事务、队列变化：在专用数据库迁移后执行 `make test-integration`，确认相应测试实际运行。
- 刷题闭环变化：按仓库约定用 HTTP 走 create → autosave → submit（幂等键）→ result；重复提交不新增判分或第二个批次 AI 任务，结果可轮询到 `aiAnalysis` 终态。AI HTTP 响应可以使用受控本地假服务，不能用是否连通付费服务替代业务测试。
- 页面变化：至少核对桌面与 390px 宽度、键盘操作、加载/空/失败状态。自动化组件测试不等于已完成浏览器视觉走查。
- 新迁移：在空测试库和已有测试数据的库中验证升级；禁止通过修改基线或重置题库完成升级。
- 有数据修复需要时：区分代码修复与用户缓存重建，列清范围；通过现有任务重算，不修改原始历史事实。

建议执行记录格式：

```text
未验证：<例如未做手机走查；没有则写无>
```
