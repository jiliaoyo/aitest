# AI 刷题 App 后端框架结构规范

> 版本：v0.1  
> 技术栈：Go + PostgreSQL  
> 架构：模块化单体 + 同代码库异步 worker  
> 依据：产品需求文档与前端设计审核

## 1. 目标

这份规范约束首版后端的目录、模块边界、数据可信度、接口契约和异步任务。目标不是提前搭建通用平台，而是安全地支撑：

- 批次创建、自动保存、整批提交和判分。
- 标准答案与 AI 判定严格分层。
- 题目修改后历史练习仍可复现。
- 账号数据和管理权限严格隔离。
- 非结构化题库异步整理、人工审核后发布。
- 可重算的学习统计和可解释推荐。

## 2. 架构决策

### 2.1 首版形态

```text
Vue Web
   │ HTTPS / JSON
   ▼
Go API 单体 ───────────────┐
   │                       │
   ├── PostgreSQL          ├── AI HTTP API
   │   ├── 业务数据        │
   │   └── jobs 任务表     └── 本地持久卷中的导入原文件
   │
Go Worker（同一代码库、独立进程）
```

- API 和 worker 共用领域代码与数据库。
- 开发环境可在一个进程中同时启动 API 和 worker；生产环境分成两个进程，便于独立重启。
- 首版不拆微服务，不引入 Redis、Kafka、向量数据库、Elasticsearch 或工作流引擎。
- 首版文件保存在受限的持久目录；需要多实例部署时再换 S3 兼容对象存储。

### 2.2 最小依赖

| 用途 | 选择 |
| --- | --- |
| HTTP 路由与中间件 | Go `net/http` |
| JSON | `encoding/json` |
| 日志 | `log/slog` |
| PostgreSQL | `github.com/jackc/pgx/v5` |
| 密码哈希 | `golang.org/x/crypto/bcrypt` |
| 数据库迁移 | `goose` CLI，只用于开发和部署 |
| AI 调用 | `net/http`，不绑定厂商 SDK |
| 配置 | 环境变量 + 显式解析，不引入配置框架 |

暂不使用 ORM、依赖注入框架、通用 Repository、事件总线或 Go Web 框架。真实重复出现后再抽象。

模块内只按真实需要添加文件，通常从以下四个开始：

```text

├── handler.go   # HTTP 参数、鉴权上下文、响应 DTO
├── service.go   # 业务流程和事务边界

└── model.go     # 领域结构、枚举、校验
```

不要为每个模块机械创建空文件，也不要建立一层只有转发功能的 controller/service/repository 接口。

## 4. 依赖方向

```text
cmd
 └── app
      ├── httpapi ──► auth/catalog/content/practice/learning/imports
      ├── jobs    ──► practice/learning/imports/ai
      └── store/files/ai
```

规则：

- `cmd` 只读取配置、组装依赖、处理关闭信号。
- `httpapi` 只放跨模块 HTTP 能力；业务 handler 跟随所属模块。
- handler 负责解析和输出，service 负责业务，store 负责 SQL。
- 模块直接依赖具体结构体，不为单一实现创建接口。
- 只有测试确实需要替换外部系统，或出现第二个实现时，才在使用方定义窄接口。
- 模块间共享业务不能放进 `utils`；由真正拥有该规则的模块提供方法。
- 数据库事务由 service 开启并传给本模块 store，不在 handler 中控制事务。

## 5. 领域模块职责

### 5.1 `auth`

- 邮箱注册、登录、退出、找回密码。
- 使用随机不透明 session token；浏览器只保存 `HttpOnly + Secure + SameSite=Lax` Cookie。
- 数据库只保存 token 的 SHA-256 哈希，不保存明文 token。
- 将 `userID` 和 `role` 写入请求 context。
- 管理端中间件只负责提前拒绝；store 查询仍需带用户或角色条件。

### 5.2 `catalog`

- 考试、级别、科目和知识点树。
- 知识点正文、发布状态和层级校验。
- 提供创建练习和后台编辑需要的分类查询。
- “综合”是筛选模式，不写入知识点表。

### 5.3 `content`

- 来源、来源章节、材料、题目、选项和标准答案。
- 管理题目不可变版本与发布状态。
- 标准答案放在独立私有表，学习端题目查询不连接该表。
- AI 推测答案不能写入标准答案表。

### 5.4 `practice`

- 题目可用数量、选题、创建批次。
- 自动保存、标记待检查、整批提交。
- 确定性判分、AI 判分任务创建和结果聚合。
- 生成严格区分“答题前”和“答题后”的 DTO。

### 5.5 `learning`

- 做题历史、错题本、知识点统计和仪表盘。
- 从原始判分结果更新或重算统计。
- 推荐使用明确 SQL 规则；AI 只把计算结果改写成建议文案。
- 默认只有官方和人工审核结果计入正式正确率；AI 结果单独统计。

### 5.6 `imports`

- 文件上传、校验、文字提取、AI 整理草稿和人工审核。
- 原文件、提取文本、AI 输出和人工修订均可追溯。
- 文本、Markdown、CSV 先使用标准库处理；DOCX 可用 `archive/zip` + `encoding/xml` 提取文本。
- PDF 提取在拿到真实样本后选一个成熟实现，不自写 PDF 解析器。
- 扫描件 OCR 不属于 P0。

### 5.7 `jobs`

- PostgreSQL 任务表的创建、领取、续租、重试和失败。
- worker 按 `kind` 调用具体处理函数；首版用一个明确的 `switch`，不做插件注册框架。
- 业务数据变更与任务入队在同一数据库事务中完成。

### 5.8 `ai`

- 一个带超时的 HTTP client。
- 固定版本的 prompt 模板，通过 `go:embed` 打包。
- 对 AI JSON 输出执行严格解码和业务校验。
- 记录模型、提示词版本、输入对象版本、耗时、用量和错误。
- 不读取用户邮箱、姓名、Cookie 等无关数据。

### 5.9 `files`

- 校验扩展名、MIME、大小和 SHA-256。
- 将原文件保存到不可由 Web 服务器直接遍历的持久目录。
- 文件名由服务端生成，原始文件名仅作为元数据。
- 文件读取必须通过管理员鉴权接口。

## 6. 数据库设计规则

### 6.1 通用规则

- PostgreSQL 负责外键、唯一约束、检查约束和事务一致性。
- 主键使用 PostgreSQL 生成的 UUID；时间统一保存 `timestamptz`。
- 状态字段使用 `text + CHECK`，避免首版频繁迁移 PostgreSQL enum。
- 所有表包含 `created_at`，可修改记录包含 `updated_at`。
- 已发布内容不物理删除，使用 `retired_at` 或状态下架。
- 用户所属记录的查询必须包含 `user_id` 条件。
- JSON 只用于选项、答案值、AI 输入输出等结构灵活的小字段，不把整套关系数据塞进一个 JSON。

### 6.2 最小表集合

| 模块 | 表 | 关键用途 |
| --- | --- | --- |
| auth | `users` | 邮箱、密码哈希、角色、默认级别 |
| auth | `auth_sessions` | session token 哈希、过期和失效时间 |
| auth | `password_reset_tokens` | 一次性找回密码令牌 |
| catalog | `exams` | JLPT 及未来考试 |
| catalog | `exam_levels` | N1–N5 |
| catalog | `subjects` | 文字词汇、语法、阅读 |
| catalog | `knowledge_points` | 层级、正文、发布状态 |
| content | `sources` | 书籍、试卷、自建来源与授权信息 |
| content | `source_sections` | 章节或年份 |
| content | `materials` | 材料身份和当前版本 |
| content | `material_versions` | 不可变材料正文 |
| content | `questions` | 题目身份、状态和当前版本 |
| content | `question_versions` | 不可变题干、题型、选项和分类引用 |
| content | `question_version_knowledge_points` | 版本与知识点多对多关系 |
| content | `answer_keys` | 私有标准答案、权威来源和来源解析 |
| practice | `practice_sessions` | 用户批次、状态、筛选与提交幂等信息 |
| practice | `practice_items` | 顺序和不可变题目版本引用 |
| practice | `user_answers` | 自动保存答案、标记和提交时间 |
| practice | `grading_results` | 判分、来源、状态和解析 |
| learning | `user_knowledge_stats` | 可重算的聚合统计 |
| learning | `issue_reports` | 题目、答案、解析或分类举报 |
| imports | `import_jobs` | 文件与总体处理状态 |
| imports | `import_items` | 原文位置、AI 草稿、异常和审核状态 |
| jobs | `jobs` | 通用异步任务队列 |
| ai | `ai_runs` | AI 调用审计与用量 |
| shared | `audit_logs` | 管理员发布、下架和修订记录 |

### 6.3 题目版本与答案隔离

```text
questions.current_version_id
             │
             ▼
question_versions ──► material_versions
       │
       ├──► question_version_knowledge_points
       │
       └──► answer_keys  （仅判分和管理端查询）

practice_items.question_version_id
```

- 管理员编辑已发布题目时创建新版本，不修改旧版本。
- 新练习只使用 `questions.current_version_id` 指向的已发布版本。
- 历史批次通过 `practice_items.question_version_id` 继续读取原内容。
- `answer_keys` 与公开题目内容分表，学习端查询根本不选答案字段。
- `answer_keys.authority` 只允许 `official`、`human_verified`。
- 没有标准答案时不创建 `answer_keys` 记录；AI 结果只写 `grading_results`。

### 6.4 关键约束

- `users.email_normalized` 唯一。
- 同一 `practice_session` 的 `position` 唯一。
- 同一批次同一题目只能有一条当前 `user_answers`。
- 同一批次题目同一判分来源只有一条当前 `grading_results`。
- `practice_sessions(user_id, status, created_at)` 建组合索引。
- `questions(status, current_version_id)`、题目级别和科目字段建立选题索引。
- `jobs(status, available_at)` 建领取索引。
- `question_versions.options` 和 `answer_keys.value` 使用 JSON Schema 等价的 Go 校验，数据库再检查基础 JSON 类型。

## 7. 业务状态

### 7.1 练习批次

```text
active ──submit──► grading ──all done──► completed
                         └──retries exhausted──► analysis_failed
```

- `active`：允许保存和提交。
- `grading`：确定性结果已可见，AI 任务仍在运行。
- `completed`：所有需要的判分已结束。
- `analysis_failed`：保留已知结果，失败题显示可重试。

### 7.2 单题判分

- `pending`：等待 AI。
- `correct` / `incorrect`：已有结果。
- `unanswered`：用户未作答，不调用 AI；有权威答案时仍计入正式题数并按错误统计，无权威答案时不进入任何正确率。
- `failed`：超过重试次数。
- `source` 为 `deterministic` 或 `ai`。
- `answer_authority` 只在确定性结果中为 `official` 或 `human_verified`。

### 7.3 内容

```text
draft ─► in_review ─► published ─► retired
  ▲          │
  └──────────┘
```

发布必须在事务中检查题干、题型、分类、材料关系和答案一致性。没有答案允许发布，但必须产生警告并在练习选题时可识别。

### 7.4 导入任务

```text
uploaded ─► extracting ─► structuring ─► review_ready ─► published
                 │              │               │
                 └──────────────┴──────────────► failed
```

`failed` 保存阶段和可读错误；管理员可从安全阶段重试，不能重复创建已发布题目。

## 8. HTTP API 规范

### 8.1 通用约定

- 前缀：`/api/v1`。
- JSON 字段：`camelCase`。
- ID：字符串 UUID。
- 时间：UTC 的 RFC 3339。
- 枚举：小写 `snake_case`。
- 写接口只接受 `Content-Type: application/json`，上传接口除外。
- JSON body 使用 `http.MaxBytesReader` 限制大小，并拒绝未知字段。
- 列表使用游标分页：`?cursor=&limit=`，默认 20，最大 100。
- 所有错误使用统一结构：

```json
{
  "error": {
    "code": "practice_not_active",
    "message": "该练习已提交，不能继续修改",
    "requestId": "..."
  }
}
```

`message` 用于用户提示，前端分支判断只使用稳定的 `code`。

## 9. 答题前与答题后 DTO

### 9.1 答题前

```json
{
  "id": "session-id",
  "status": "active",
  "answeredCount": 6,
  "items": [
    {
      "id": "item-id",
      "position": 8,
      "type": "single_choice",
      "material": null,
      "stem": "この店は、駅から近い（　　）、いつも混んでいる。",
      "options": [
        {"id": "a", "label": "A", "text": "にしては"},
        {"id": "b", "label": "B", "text": "ことから"}
      ],
      "savedAnswer": {"optionIds": ["b"]},
      "markedForReview": true,
      "savedAt": "2026-09-01T01:42:00Z"
    }
  ]
}
```

答题前禁止出现：

- `correctAnswer`、`answerKey`、`answerAuthority`。
- 官方或 AI 解析。
- 正确/错误状态。
- 不是原题一部分的翻译、知识点答案提示或难度解释。

### 9.2 答题后

```json
{
  "id": "session-id",
  "status": "grading",
  "summary": {
    "confirmed": {"correct": 14, "total": 18, "accuracy": 0.7778},
    "ai": {"correct": 1, "completed": 1, "pending": 1, "failed": 0}
  },
  "items": [
    {
      "id": "item-id",
      "position": 8,
      "userAnswer": {"optionIds": ["b"]},
      "gradingStatus": "incorrect",
      "gradingSource": "deterministic",
      "answerAuthority": "human_verified",
      "correctAnswer": {"optionIds": ["c"]},
      "explanation": {
        "text": "...",
        "source": "ai"
      }
    }
  ]
}
```

- `confirmed.accuracy` 由后端计算，前端只格式化显示。
- AI 未完成时不计算完整 AI 正确率。
- `explanation.source` 独立于答案权威；标准答案可以搭配 AI 解析。

## 10. 练习事务与竞态处理

### 10.1 创建批次

1. 校验用户、级别、科目、范围和题量。
2. 在一个事务内选择已发布题目的当前版本。
3. 写入 `practice_sessions` 和有顺序的 `practice_items`。
4. 返回答题前 DTO，不查询 `answer_keys`。

题量不足时返回 `409 insufficient_questions` 和实际可用数，前端确认后用较小题量重新创建；服务端不静默扩大范围。

### 10.2 自动保存

- `PUT` 对 `(session_id, item_id)` 执行 upsert。
- SQL 同时校验 `session.user_id` 和 `session.status = 'active'`。
- 提交后保存返回 `409 practice_not_active`。
- 返回服务端 `savedAt`，前端用它展示已保存状态。

### 10.3 整批提交

提交请求必须携带当前全部最终答案，而不是假设之前的自动保存已经到达：

```json
{
  "answers": [
    {"itemId": "item-id", "value": {"optionIds": ["b"]}, "markedForReview": true}
  ]
}
```

并带 `Idempotency-Key` 请求头。

服务端在一个事务内：

1. `SELECT ... FOR UPDATE` 锁定该用户的批次。
2. 首次提交时保存幂等键与请求内容哈希。
3. 用请求中的最终答案覆盖该批次的自动保存答案。
4. 将批次由 `active` 改为 `grading`。
5. 对有权威答案的题目完成确定性判分。
6. 为需要 AI 的题目写入 `pending` 结果和 `jobs` 任务。
7. 没有 AI 任务时直接设为 `completed`。

相同幂等键和相同内容重复提交时返回现有结果；相同键但内容不同返回 `409 idempotency_conflict`；批次已提交且使用新键时返回当前批次状态，不重复判分。

## 11. 确定性判分

- 单选：选项 ID 完全相等。
- 多选：集合相等，不考虑提交顺序。
- 填空：按答案键中管理员配置的可接受值进行 Unicode 规范化、首尾空白处理后比较。
- 简答或无标准答案题：进入 AI 判定。
- 未答题：有标准答案时确定为错误；无标准答案时记录未答，不调用 AI。

判分函数必须是无副作用的纯函数，并有一张表驱动测试覆盖单选、多选、填空、未答和非法选项。

## 12. PostgreSQL 任务队列

### 12.1 `jobs` 字段

```text
id, kind, payload, status, attempts, max_attempts,
available_at, locked_by, locked_until,
last_error, created_at, updated_at
```

### 12.2 领取与租约

- worker 使用 `FOR UPDATE SKIP LOCKED` 原子领取一条到期任务。
- 领取后写 `locked_by` 和 `locked_until`。
- 长任务定时续租；进程崩溃后租约到期，其他 worker 可重新领取。
- 处理器必须按业务唯一键幂等，例如同一 `practice_item_id + grading_source` 只能写一份结果。
- 指数退避最多 3 次；超过后标记 `failed` 并保留短错误摘要。
- 管理员重试创建新的可追溯尝试，不删除失败记录。

### 12.3 任务类型

P0 只保留：

- `grade_practice_item_ai`
- `explain_practice_item_ai`
- `extract_import_file`
- `structure_import_content_ai`
- `rebuild_user_knowledge_stats`

新增任务类型前先确认不能放进现有任务处理器。

## 13. AI 调用规范

### 13.1 输入

- 题目或导入项的不可变版本 ID。
- 完成任务所需的题干、选项、材料、用户答案和已有标准答案。
- 允许选择的知识点 ID 与名称。
- 明确说明哪些字段来自原文、哪些字段允许推测。

### 13.2 输出

- 每种任务定义独立版本号，如 `practice_grade.v1`。
- `json.Decoder.DisallowUnknownFields()` 严格解码。
- 校验选项 ID、知识点 ID、字符串长度和必填字段。
- 非法 JSON 最多重试一次；业务字段非法不靠循环提示无限修复。

### 13.3 冲突规则

- 有 `answer_keys` 时，AI 不能改变判分，只能生成解析或创建内容异常举报。
- 无答案题的 AI 结论写 `grading_results(source='ai')`。
- 导入时 AI 推测答案只保存在 `import_items.ai_draft`，管理员确认后才写 `answer_keys(authority='human_verified')`。
- AI 失败时保留确定性成绩和用户答案，批次最终进入 `analysis_failed`。

## 14. 学习统计与推荐

### 14.1 事实来源

- `user_answers` 和 `grading_results` 是原始事实。
- `user_knowledge_stats` 是缓存，可从原始事实重算。
- 正式正确率只聚合 `answer_authority in ('official', 'human_verified')`。
- AI 判定保留独立计数，不参与“已确认掌握度”。

### 14.2 首版推荐规则

按以下稳定规则排序：

1. 最近 30 天已确认作答至少 5 题。
2. 近期正确率升序。
3. 连续错误数降序。
4. 最近练习时间升序。

返回推荐原因所需的原始数字，AI 只把这些数字组织成自然语言。样本不足时返回综合练习建议，不输出虚假的薄弱结论。

## 15. 安全规范

- 生产环境前后端同源部署，避免不必要的 CORS 和跨站 Cookie 配置。
- 所有非 GET 请求校验 `Origin`，Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 登录和密码重置接口按 IP 与邮箱做基础限流；计数先存 PostgreSQL。
- 密码重置令牌与 session token 均只保存哈希并设置过期时间。
- 管理端路由统一角色中间件，内容发布 service 再校验管理员身份。
- 用户资源 SQL 使用 `WHERE id = $1 AND user_id = $2`，不能先按 ID 查询再在 Go 中判断。
- 上传限制格式、MIME、10 MB 默认大小和解压后总大小，防止压缩炸弹。
- AI 输入去除账号身份字段；日志不记录 Cookie、token、密码和完整用户答案正文。
- 健康检查分 `/health/live` 和 `/health/ready`，ready 检查数据库连接，不检查 AI 服务。

## 17. 日志与可观测性

- 每个请求生成或透传 `request_id`，写入响应头和错误体。
- `slog` 使用 JSON 输出：请求方法、路径模板、状态码、耗时、用户 ID、请求 ID。
- worker 记录 job ID、kind、attempt、耗时和结果，不打印完整 payload。
- `ai_runs` 记录模型、提示词版本、输入版本、用量、耗时和错误类型。
- 首版暴露简单 `/metrics` 之前，先确保结构化日志能计算接口错误、任务失败和 AI 成本。

## 18. 测试规范

### 18.1 最小必测

1. 答题前响应序列化后不含答案、解析和判分字段。
2. 自动保存与提交并发时，提交请求携带的最终答案胜出。
3. 相同幂等键重复提交只产生一组判分结果和 AI 任务。
4. 官方或人工答案永远覆盖不了，也不会被 AI 结果替代。
5. 题目发布新版本后，旧批次仍读取旧版本。
6. 普通用户访问管理接口返回 403。
7. 用户访问他人批次、答案和统计统一返回 404。
8. AI 部分失败时确定性成绩仍正确，批次进入正确状态。
9. 同一导入任务重复执行不会重复发布题目。

### 18.2 测试方式

- 判分、状态转换和校验使用 Go 表驱动单元测试。
- SQL 事务、权限和并发使用真实 PostgreSQL 集成测试。
- HTTP 使用 `httptest`，不为 handler 引入 mock 框架。
- 测试 fixture 保持最小：一个管理员、两个用户、一套级别、一个材料题、一个有答案题和一个无答案题。

## 19. 编码规范

- 使用当前稳定 Go 版本，并在 `go.mod` 固定。
- 所有可能阻塞的方法第一个参数是 `context.Context`。
- 使用 `%w` 包装错误；HTTP 状态映射集中在 `httpapi/errors.go`。
- 禁止 `panic` 处理用户输入、数据库错误或 AI 错误。
- handler 不拼 SQL，store 不返回 HTTP 状态码。
- DTO 与数据库 model 分开，尤其不能把包含答案的管理端 model 直接序列化给学习端。
- 枚举使用命名字符串类型和显式校验。
- 金额不存在，不引入 decimal；时间全部 UTC，前端负责时区显示。
- 不创建 `utils`、`helpers`、`common` 大杂烩包。
- 新增一个分支、解析器或事务规则时，留下一个最小可运行测试。

## 20. 开发顺序

### 阶段 1：基础与可靠刷题

1. 初始化 Go module、配置、日志、数据库和迁移。
2. 完成用户、Cookie session 和管理员鉴权。
3. 完成分类、题目不可变版本和私有答案表。
4. 完成批次创建、答题前 DTO 和自动保存。
5. 完成提交事务、确定性判分、结果与历史。

### 阶段 2：学习档案

1. 知识点统计重算。
2. 仪表盘、错题本、知识点页面。
3. 可解释的薄弱点推荐。

### 阶段 3：AI 与导入

1. PostgreSQL worker 和 AI 审计。
2. 无答案题判定与 AI 解析。
3. 文件上传、文本提取、AI 结构化草稿。
4. 管理审核、发布和举报处理。

不要在阶段 1 为阶段 3 预建通用工作流框架；只提前保留答案隔离、版本和任务表这三个必要边界。

## 21. 首版明确跳过

- 微服务、领域事件总线和分布式事务。
- Redis session、Redis queue 和 Kafka。
- ORM、GraphQL 和全量代码生成。
- 向量数据库、推荐模型和实时画像。
- 多 AI 提供商抽象；出现第二个提供商后再抽接口。
- 对象存储抽象；单机持久卷不足时改为一个具体 S3 实现。
- 自写 PDF 解析器和 OCR。

这些能力只在实际容量、部署或内容样本证明现有方案不够时增加。
